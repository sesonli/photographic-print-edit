# 交付记录约定

单张简单修复可只记录源文件、输出文件、改动和验收结果。批量、多版本或需要后续查找时使用 JSON 索引。路径以交付目录为基准，公开示例只使用虚构编号和相对路径。

## 记录示例

```json
{
  "source_id": "PHOTO-001",
  "source_file": "originals/PHOTO-001.jpg",
  "source_dimensions": [6000, 4000],
  "versions": [
    {
      "version_id": "v02-tree-removed",
      "output_file": "edited/PHOTO-001-v02-tree-removed.png",
      "output_dimensions": [6000, 4000],
      "intent": "去除左侧树，保留雪峰、右侧红叶与原有光色",
      "source_type": "camera-jpeg",
      "edits": ["去除左侧树及细枝", "重建其遮挡的天空与远景"],
      "ai_scope": "局部去物；天空与远景补全为生成内容",
      "method": "本次实际使用的编辑工具及操作方式",
      "review": {
        "status": "passed",
        "checks": ["缩图主次", "整幅构图与光色", "原树位置和山脊边缘", "右侧红叶保护"],
        "limitations": ["生成区域不代表被遮挡场景的真实记录"]
      }
    }
  ]
}
```

上例的尺寸仅作格式示范，真实任务须读取实际文件。没有执行的检查不要写入 `checks`，没有测量的尺寸不要填猜测值。`review.status` 可按实际状态写为 `candidate`、`rework` 或 `passed`。

## 文件与清单核对

- 原片编号应来自明确映射，不以目录排序或任务返回顺序代替。相机编号重复时加入目录或唯一批次信息，避免跨目录混配。
- 每个输出路径都应存在且可解码；核对像素尺寸、方向、颜色显示与索引一致。
- 对照页从经审核的成片派生。原片和版本保留自己的比例，不拉伸至同一形状。
- 只把已通过的作品列为正式成片。预览小图、候选和中间补片不计入成片数量。
- 需要可重放时额外保存本次真实使用的配方、蒙版、提示词和工具信息；不要将 JPEG 或文字描述称作可编辑工程文件。
- 对外分享方法时仅放通用规则与脱敏示例。私人照片、EXIF 定位、绝对路径、账号资料和会话导出须按用户授权另行处理。

## 长任务与恢复

多图、多版或可能中断的任务，在完成一版后保存其 `source_id`、`version_id`、实际输出路径、状态及已完成的检查。必要时记录文件哈希、使用的底图、蒙版和下一步；不要求简单单图任务建立完整数据库。重连后先读取现有清单、检查文件存在及对应关系，再继续缺项；不能因会话丢失重做合格版本，也不能把有文件当作已验收。

按用户指定标记筛选时，按完整文件名或明确字段核对。例如“文件名末尾标了 -G”应匹配扩展名前的 `-G`，不能将含有 `-group` 的文件混入。记录入选清单再传输，避免依赖图库排序。

严格局部修复额外记录 `preservation_baseline`、编辑蒙版、最终输出与差异报告。允许调色并换天时，声明“经调色的实拍底板”作为合成验证基准，不声称相对原片 RGB 完全不变。记录各阶段的真实检查，详见[局部 AI 与保真验证](local-ai.md)。

## 已授权的公开发布

照片精修本身不包含自动发布许可；用户已明确要求发布时沿用授权，使用环境中适用的发布工具。导出的公开图片要检查姓名、署名、联系方式及定位元数据是否属于本次公开内容。参考作品的署名和账户实名不是默认文案。

发布后修改已有作品时，先确认目标作品，替换指定图片并保持其顺序、标题、正文和其余图片；保存后重新打开，核对修正确已生效。不要用新增帖子代替用户要求的原帖修改。平台可能压缩图片，本地像素保真报告不等于线上压缩副本像素完全相同。
